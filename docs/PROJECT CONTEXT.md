# PROJECT CONTEXT

## 1. Проект

«Арена» — Telegram-бот и Telegram Mini App для самостоятельной подготовки к ЕГЭ по информатике.

Основные возможности текущей версии:

- Учёт прогресса участников по 27 заданиям ЕГЭ.

- Учёт общего количества решённых задач.

- Учёт результатов пробных экзаменов.

- Расчёт общего прогресса и рейтинга участников.

- Недельная и месячная статистика.

- Административное управление участниками и их прогрессом.

- Журналирование изменений.

Репозиторий: `IvanIlinov/kimi`.

## 2. Технологии

- Backend: Node.js, TypeScript.

- Frontend: Preact, TypeScript, Vite.

- База данных: SQLite через встроенный `node:sqlite`.

- Взаимодействие: Telegram Bot API и Telegram Web Apps API.

- HTTP API обслуживается backend-приложением.

### Выкладка в Staging

1. Запусти [локальные проверки](PROJECT%20QUICKSTART.md#локальный-запуск-и-проверки), закоммить согласованные изменения в `development` и отправь ветку на GitHub. Запомни полный хеш проверяемого коммита.

   ```bash
   git push origin development
   git rev-parse HEAD
   ```

2. Для изменений backend обнови рабочий каталог Staging и перезапусти тестовый сервис по [общей процедуре](#обновление-backend-на-vps). Предпросмотр гостя и ученика включается строкой `STAGING_PREVIEW_ENABLED=1` в `.env.staging`. Проверить настройку из каталога сервиса можно без вывода файла.

   ```bash
   node --env-file=.env.staging -e 'process.exit(process.env.STAGING_PREVIEW_ENABLED === "1" ? 0 : 1)'
   ```

3. [Проверь API и Mini App](#проверка-выкладки) на тестовых адресах. Через тестового бота проверь открытие Mini App, нужные операции сохранения и предпросмотр админки.

В рейтинге Staging есть вымышленные профили Алисы, Бориса, Веры и Глеба с разными статусами заданий и значениями прогресса. Они заведены только в тестовой базе, Telegram-аккаунтов для них нет. Открыть их можно из рейтинга.

### Выкладка в Production

Релиз начинается после явного разрешения на Production и проверки конкретного коммита на Staging.

1. Проверь ветку `main`, чистоту рабочего каталога `/home/arena/bot` и состояние `arena-bot.service`. Для релиза с изменениями SQLite сначала сделай [резервную копию и пробную миграцию](#резервная-копия-sqlite).
2. С локального компьютера обнови `main` до согласованного коммита обычным fast-forward. В примере `release` — полный хеш проверенного коммита из `development`.

   ```bash
   release='<полный хеш проверенного коммита>'
   git fetch origin main &&
   git merge-base --is-ancestor origin/main "$release" &&
   git push origin "$release:refs/heads/main"
   ```

3. Если релиз меняет backend, обнови Production по [общей процедуре](#обновление-backend-на-vps). Для правки только фронтенда или документации достаточно публикации из `main`. Для таких правок checkout и запущенный backend на VPS могут оставаться на предыдущем коммите.
4. [Проверь API и Mini App](#проверка-выкладки) на рабочих адресах. В Production оставь `STAGING_PREVIEW_ENABLED` выключенным. Блок «Предпросмотр» скрыт, запросы предпросмотра отклоняются, редактирование результатов ученика через рейтинг доступно администратору.

### Обновление backend на VPS

Подключись к VPS, подставь ожидаемый полный хеш релиза и выбери окружение в `target`. Команды проверяют каталог, ветку и коммит перед обновлением. Сервисы работают под пользователем `arena` с `Restart=always`. Когда `sudo` требует пароль, проверенный способ перезапуска — послать `SIGTERM` главному процессу выбранного сервиса после проверки владельца и cgroup. Результат подтверждают новый PID и ответ локального API.

```bash
(
    set -eu
    target=staging
    release='<полный хеш проверенного коммита>'
    case "$target" in
        staging)
            app=/home/arena/staging; branch=development
            service=arena-staging.service; port=3001
            ;;
        production)
            app=/home/arena/bot; branch=main
            service=arena-bot.service; port=3002
            ;;
        *) exit 1 ;;
    esac

    cd "$app"
    test "$(git branch --show-current)" = "$branch"
    test -z "$(git status --porcelain)"
    test "$(systemctl show "$service" -p WorkingDirectory --value)" = "$app"
    test "$(systemctl show "$service" -p User --value)" = "$(id -un)"
    test "$(systemctl show "$service" -p Restart --value)" = always

    git fetch origin "$branch"
    test "$(git rev-parse FETCH_HEAD)" = "$release"
    git merge --ff-only FETCH_HEAD

    old_pid="$(systemctl show "$service" -p MainPID --value)"
    test "$old_pid" -gt 1
    test "$(stat -c %U "/proc/$old_pid")" = "$(id -un)"
    cut -d: -f3 "/proc/$old_pid/cgroup" | grep -Fxq "/system.slice/$service"
    kill -TERM "$old_pid"

    for attempt in $(seq 1 25); do
        new_pid="$(systemctl show "$service" -p MainPID --value)"
        if test "$new_pid" -gt 1 && test "$new_pid" != "$old_pid" &&
            systemctl is-active --quiet "$service" &&
            curl -fsS --max-time 2 "http://127.0.0.1:$port/api/health"; then
            exit 0
        fi
        sleep 1
    done
    systemctl status "$service" --no-pager
    exit 1
)
```

### Резервная копия SQLite

На VPS выполни из Production. SQLite `.backup` создаёт согласованный снимок работающей базы. Копия хранится в отдельном каталоге с доступом для владельца. Для прогона миграций используется второй файл и код из уже проверенного checkout Staging.

```bash
(
    set -eu
    cd /home/arena/bot
    release='<полный хеш проверенного коммита>'
    test "$(git branch --show-current)" = main
    test "$(git -C /home/arena/staging rev-parse HEAD)" = "$release"
    umask 077
    db_path="$(node --env-file=.env -p 'process.env.DB_PATH ?? "data/arena.db"')"
    test -f "$db_path"
    mkdir -p /home/arena/backups
    backup_dir="$(mktemp -d /home/arena/backups/arena-prod.XXXXXX)"
    sqlite3 -readonly "$db_path" ".timeout 10000" ".backup $backup_dir/pre-release.db"
    test "$(sqlite3 -readonly "$backup_dir/pre-release.db" 'PRAGMA integrity_check;')" = ok
    cp "$backup_dir/pre-release.db" "$backup_dir/migration-check.db"
    DB_PATH="$backup_dir/migration-check.db" node --disable-warning=ExperimentalWarning --input-type=module -e '
        const { db } = await import("/home/arena/staging/src/db.ts");
        db.close();
    '
    test "$(sqlite3 -readonly "$backup_dir/migration-check.db" 'PRAGMA integrity_check;')" = ok
    test -z "$(sqlite3 -readonly "$backup_dir/migration-check.db" 'PRAGMA foreign_key_check;')"
    printf 'Резервная копия: %s\n' "$backup_dir/pre-release.db"
)
```

Для миграции данных проверь на копии и ожидаемые изменения записей. Например, при приведении имён к заглавной букве сравни число записей, сами преобразования и поля, не связанные с именем.

### Изоляция Staging и Production

Staging — полноценное отдельное тестовое окружение, изолированное от Production.

У него есть собственные:

- Подключение к отдельному проекту Vercel.

- Тестовый Telegram-бот, не связанный с пользователями Production.

- Отдельная база данных, не содержащая рабочие данные Production.

Изменения и проверки в Staging не должны затрагивать Production. При работе с переменными окружения, токенами ботов, базами данных и настройками Vercel всегда учитывать, к какому окружению они относятся.

Не переносить настройки, секреты и данные между окружениями без явного разрешения пользователя.

### Правила работы с окружениями

- Разрабатывать и проверять изменения локально.

- Не использовать Production как рабочую среду разработки.

- Не изменять Production и серверную конфигурацию без явного разрешения пользователя.

- Не выполнять `push`, `merge`, деплой и другие операции, изменяющие удалённые окружения, без разрешения пользователя.

- Перед серверными операциями проверять директорию, ветку и состояние Git.

- Не предполагать, что Staging и Production обновляются автоматически. Сначала проверять существующий процесс деплоя.

### Доступы и безопасность

- Использовать уже настроенные SSH-ключи и средства авторизации.

- Не выводить содержимое `.env`, `.env.staging`, SSH-ключей и других файлов с секретами.

- Не записывать пароли, токены, приватные идентификаторы и секреты в документацию.

- Не изменять SSH-конфигурацию и права доступа без необходимости и согласования.

- Не выполнять команды, последствия которых для Production или VPS неясны.

## 4. Участники и прогресс

В проекте учитываются следующие показатели:

- `topics` — задания ЕГЭ, всего 27.

- `tasksTotal` — общее количество решённых задач.

- `tasksWeek` — количество решённых задач за текущую неделю.

- `exam` — результат пробного экзамена от 0 до 100. У нового ученика начальное значение 0. Mini App также показывает 0 для записей с `NULL`.

### Статусы заданий

Каждое задание имеет один из четырёх статусов:

- `todo` — ещё не изучается.

- `learning` — изучается.

- `done` — изучено, но ещё не закреплено.

- `reinforced` — окончательно освоено.

Переходы выполняются по кругу:

`todo → learning → done → reinforced → todo`

Только `reinforced` учитывается как окончательно освоенное задание.

## 5. Расчёт прогресса и рейтинга

### Общий прогресс

Максимальные ориентиры:

- 27 закреплённых заданий.

- 900 решённых задач.

- 100 баллов за пробный экзамен.

Вес показателей:

- Закреплённые задания — 40%.

- Решённые задачи — 40%.

- Результат пробного экзамена — 20%.

Каждый показатель ограничивается своим максимумом. Общий прогресс округляется до целого процента.

### Рейтинг XP

Формула:

`XP = 100 × reinforced + tasksTotal + 3 × exam`

Участники сортируются по убыванию XP. При равенстве XP место одинаковое.

XP используется для места в профиле и сортировки рейтинга в Telegram-боте.

### Экран «Рейтинг» в Mini App

Экран доступен ученикам, гостям и администраторам. У него три вкладки:

- «Глобальный» — по проценту общего прогресса.
- «Месяц» — по проценту выполнения месячных целей.
- «Неделя» — по числу решённых за неделю задач. При равенстве учитывается изменение числа закреплённых за неделю заданий.

Во вкладке «Месяц» рядом со шкалой участника показано число решённых задач относительно накопительной цели месяца. В карточке лидера при отсутствии балла пробника отображается 0.

При равенстве по метрикам вкладки сохраняется порядок рейтинга XP. Карточка лидера соответствует первой строке. Администраторы и гости видят всех активных участников. Ученик видит первые 10 строк и свою строку, если он вне десятки. Для гостя этот экран открывается как единственная вкладка «Главная».

## 6. Цели и временные периоды

### Постоянные ориентиры

- Всего заданий: 27.

- Цель по решённым задачам: 900.

- Максимум пробного экзамена: 100.

- Недельная цель: 25 задач.

### Главная и задания ученика

Главная показывает общий прогресс, место по XP и текущие показатели. Нижняя свайп-карточка содержит прогресс месяца и недели, отсчёт до 31 мая по Москве с подписью «до начала экзаменов» и остатки до ближайших целей. Новый учебный период начинается 1 сентября, а с июня по август счётчик дней равен нулю.

Профиль из рейтинга открывает общую главную ученика с данными выбранного участника. Для ученика и гостя это режим чтения.

Во вкладке «Задания» шкала под кнопками изменения числа задач показывает недельный прогресс к цели в 25 задач. Кнопка «По плану» переключает сетку заданий между числовым порядком и последовательностью из таблицы рангов. На главной и в поле пробника отсутствие балла отображается как 0.

### Админка Mini App

Поведение экранов описано в [разделе v5 роадмапа](PROJECT_ROADMAP.md#администратор).

- `GET /api/admin/home` отдаёт посещаемость, расписание недели, выручку текущего месяца и флаг доступности предпросмотра. Стоимость урока хранится целым числом копеек. Выручка группируется по дате урока и учитывает оплаченные занятия.
- `GET /api/admin/history` возвращает историю с разбивкой по датам и ученикам. `GET /api/admin/journal` возвращает исходный журнал отдельных событий, включая административные действия.
- Посещение интерфейса ученика из рейтинга позволяет администратору править только результаты ученика. Записи сохраняются с Telegram ID администратора. Итоговые значения и общий рейтинг учитывают правки. Месячная цель по заданиям использует все текущие статусы «Закреплено», включая админские правки. Недельный прирост и месячные цели по решённым задачам и пробнику строятся по учебной активности.

### Месячные цели

Месячные цели заданы в `MONTH_GOALS` в `src/logic.ts`.

Они содержат три накопительных показателя:

- Количество закреплённых заданий.

- Количество решённых задач.

- Балл пробного экзамена.

Цели рассчитаны на период с сентября по май. С июня по август применяются майские значения. Пример накопительной цели — 16 закреплённых заданий к концу ноября. В неё входят текущие закреплённые задания с начала учебного года, включая статусы, выставленные администратором.

Месячный процент рассчитывается с теми же весами, что и общий прогресс: 40% / 40% / 20%.

### Московское время

Расчёты недельных и месячных периодов используют московское время (UTC+3).

Новая неделя начинается в понедельник в 00:00 по Москве. Осень закрывается 1 декабря, зима — 1 марта, весна и учебный год — 1 июня. Эти периоды также закрываются в 00:00 по Москве. При первом входе после закрытия периода Mini App автоматически показывает итоги один раз на аккаунт. Если готовы несколько карточек, он показывает итоги последнего завершённого сезона или года с приоритетом года при совпадении дат закрытия. Карточки недели, сезона и учебного года доступны на левой странице блока прогресса, в том числе при просмотре профиля из рейтинга. При ручном открытии «Неделя» показывает текущий результат и позволяет переключиться на прошлую неделю. С сентября по ноябрь карточка сезона показывает текущую осень и открывается вручную до её завершения.

## 7. База данных

Используется SQLite через `node:sqlite`.

Подключение и схема находятся в `src/db.ts`.

Основные таблицы:

| Таблица        | Назначение                                                                      |
| -------------- | ------------------------------------------------------------------------------- |
| `users`        | Участники, Telegram ID, имя, результат пробника, комментарий и признак удаления |
| `topic_status` | Текущий статус каждого задания участника                                        |
| `task_log`     | История изменений количества решённых задач                                     |
| `topic_log`    | История изменений статусов заданий                                              |
| `meta`         | Служебные значения приложения                                                   |
| `exam_log`     | История изменения результатов пробных экзаменов                                 |
| `admin_log`    | Журнал административных действий                                                |
| `bot_visits`   | Запуски бота активными участниками                                              |
| `lessons`      | Расписание занятий по неделям, статусы и стоимость в копейках                   |

### Особенности хранения

- Telegram ID участника уникален. При сохранении имени ученика и имени в расписании убираются пробелы по краям, первая буква становится заглавной. Существующие записи приводятся к этому формату при запуске backend.

- Статус задания хранится отдельно для каждого участника и номера задания.

- Номер задания ограничен диапазоном от 1 до 27.

- Результат пробника может быть `NULL` либо числом от 0 до 100. При добавлении ученика сохраняется 0.

- Удаление участника реализовано через поле `removed`.

- Изменения задач и статусов сохраняются в журналах.

- В `task_log` предусмотрены источник записи, автор изменения и признак отмены.

- Схема БД обновляется при запуске приложения с помощью проверок и миграций.
